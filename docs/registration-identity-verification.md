# Farmer registration identity verification

Implementation and audit date: 20 October 2026. The integration is disabled by default. There is no provider account configured and no real biometric verification has been performed. Mocked tests are not evidence of real face-match accuracy, liveness effectiveness, provider availability, or legal compliance.

## Repository audit and approved scope

The working tree was clean on `main` at `3b30e7f` when this work began. The actual registration flow is a public multipart `POST /api/users/register/`, implemented by `RegisterView` and `RegisterSerializer`. It atomically creates a pending `User`, a `Farmer`, and existing `UserDocument` records. The Next.js registration form has personal, farm, and document/consent steps. Login refuses accounts that are not approved.

`UserDocument` already stores government-ID and optional RSBSA files. Its accepted government-ID choices are PhilID, Driver's License, Voter's ID, Passport, UMID, Postal ID, PRC ID and Other Government ID, with a legacy Government ID choice. These choices were preserved; provider support for each specific Philippine document must be confirmed before enabling a workflow. The form accepts front/back images or one complete PDF.

The repository does **not** implement a CBAT/SIBAT registration-approval stage. It has MAO/Admin document review and final account approval, while field officers review other livestock workflows. The developer explicitly chose to preserve that registration workflow and add scoped, read-only CBAT/SIBAT identity evidence. No new account status or field-officer approval transition was invented.

Originally, uploads were checked by extension/size only. Registration files used the default R2 storage when configured, or public `MEDIA_ROOT` locally. Serializers already returned an authenticated streaming endpoint, and Django blocked the public `/media/user_documents/` route. Private R2 configuration exists, but a live bucket policy was not audited. There was general privacy text, but no biometric-specific consent, retention mechanism, or provider integration.

Reused: registration endpoint, accepted-ID choices, User/Farmer/UserDocument, JWT authorization, reviewer barangay scopes, notification helpers, MAO document/account controls, blob-based DocumentPreviewDialog, form controls and React Query. The only new domain records are an attempt and its minimal audit events; they are not duplicate identity-document or approval models.

## Provider choice and limits

Didit's hosted V3 workflow was selected because it documents ID verification, passive liveness and face comparison, exposes distinct per-feature results, and fits a browser redirect plus Django server API integration. As checked on this date, its [free-plan documentation](https://help.didit.me/getting-started/free-plan) advertises 500 monthly checks per core feature without a card or minimum. Extra modules and usage beyond allowances can incur charges; do not enable paid features inadvertently. Its [pricing page](https://didit.me/pricing/) announces changes on November 1, 2026, so recheck before activation. No account or trial was created for the developer.

Veriff was also considered: its [published self-service plans](https://www.veriff.com/plans/self-serve) include a hosted ID/selfie flow and liveness, but the Essential plan has a monthly minimum after a limited trial. It does not fit the stated free preference as well. Separate face-comparison APIs without liveness were not substituted for this workflow.

Didit's [privacy policy](https://didit.me/terms/privacy-policy/) describes international processing, configurable retention, an unlimited default for general verification data, and default model-improvement processing with an organization opt-out. Its suitability still requires MAO/privacy-officer review of the processing agreement, subprocessors, data locations, lawful basis and disclosures under the [Philippine Data Privacy Act](https://privacy.gov.ph/data-privacy-act/). No claim of legal approval is made here.

## Data flow

1. Existing registration uploads an ID and creates a pending farmer. With `IDENTITY_ENABLED=false`, the existing manual registration process applies.
2. When enrollment is enabled, Django creates a `NOT_STARTED` attempt linked to that farmer and the existing registration document. The response includes a signed one-hour registration capability. This capability is accepted **only** by identity endpoints; it cannot log in or access portal APIs. The browser keeps it in session storage rather than a URL.
3. The farmer sees a separate biometric notice and consent checkbox. Django checks the exact policy version and records consent time and the retention notice snapshot before creating a provider session. Permanent credentials stay on the server.
4. The farmer explicitly opens Didit's hosted capture page, presents the same ID, and captures/retakes a selfie. Didit performs the configured document, passive-liveness and selfie-to-document portrait comparison. Camera permissions and capture-quality checks belong to the provider's maintained interface. SmartLivestock neither records video nor implements a local face detector.
5. The hosted flow captures its own ID image. This is not a byte-for-byte binding to the earlier local upload. The UI explicitly tells human reviewers to inspect the registration ID; neither the code nor the demonstration should claim the two files are proven identical. No provider images or biometric templates are imported into SmartLivestock.
6. Browser return parameters are not trusted. Django retrieves the decision from the fixed provider API host, verifies the provider session, workflow and opaque attempt reference, then extracts only result categories. It does not persist raw payloads, confidence scores, ID numbers, media URLs or face embeddings. No arbitrary thresholds were invented.
7. A provider-approved result is `COMPLETED` only when all three feature categories passed in a live-configured attempt. Missing/inconclusive/declined checks require human review. Sandbox results never produce real-check completion. Provider completion never changes account or document approval.
8. MAO records a reasoned assessment of the current evidence, including alternative checks where automation failed or was unavailable. The existing document-review and account-approval controls remain authoritative. The backend blocks approving an enrolled account until its current evidence has an MAO assessment. A changed result invalidates the assessment fingerprint, requiring reassessment without deleting the earlier event.

CBAT/SIBAT can open the registration-evidence dialog on their field dashboard and view only assigned-barangay farmers (or all barangays when explicitly granted). They can preview the same protected documents and read attempt history but cannot record MAO assessments, approve documents, or approve accounts. MAO sees the evidence inside the existing user-management review dialog. Notifications use existing municipal and scoped field-recipient services.

## Configuration before any real capture

The example environment file contains empty placeholders and `IDENTITY_ENABLED=false`. Obtain a Didit business account and verify its actual entitlements/approval requirements. Create a **KYC document** workflow containing separate document ID verification, liveness and face-match nodes; the face reference must be the portrait from that workflow's document, not an enrolled-user authentication reference. Retain the provider's documented/recommended decision configuration and validate it with the selected documents; do not invent confidence thresholds.

The [workflow configuration reference](https://docs.didit.me/management-api/workflows/feature-configs) documents `face_liveness_method=PASSIVE`. Configure that explicitly, disable microphone/audio recording, disable face search (`face_search_enabled=false`), and disable retained biometric templates. Confirm the hosted mobile and desktop flows use these settings. Active/3D/flashing results are not accepted as completed passive checks by this integration. Do not switch to video capture without a reviewed notice and implementation update.

Set the backend API key, workflow ID, application ID, webhook secret, sandbox/live environment, approved policy version, privacy contact, positive metadata-retention duration and a plain-language retention notice describing both local documents and third-party data. Opt out of provider model improvement; set finite provider retention and agree the DPA/transfer terms. Only then set `IDENTITY_PROVIDER_PRIVACY_CONFIRMED=true`. Missing settings keep session creation unavailable even if enrollment is enabled.

Configure the public HTTPS webhook URL as `/api/users/identity/webhook/` for V3 `status.updated` and `data.updated` events. The [documented V2 canonical HMAC](https://docs.didit.me/integration/webhooks) is checked with a bound dispatch timestamp and five-minute tolerance. Session/application/workflow/environment/vendor references must match. Event IDs are unique, stale events are ignored, and the actual decision is re-fetched server-side. Unsigned callbacks, forged signatures, client-provided scores/statuses and browser redirects cannot establish a result. Provider test-webhook deliveries are ignored for application state.

The session and decision API contracts are documented in [Create Session](https://docs.didit.me/sessions-api/create-session), [Retrieve Session](https://docs.didit.me/sessions-api/retrieve-session), and [Data models](https://docs.didit.me/reference/data-models). These references matter: the V3 `id_verifications`, `face_matches` and `liveness_checks` arrays must not be replaced with legacy V2 singular fields.

Install backend requirements (including `pypdf`), run the migration after review, configure persistent private storage, and deploy the backend/frontend together. No production database migration was executed during this task.

## Storage, retention, failure and recovery

New local registration documents use `PRIVATE_DOCUMENT_ROOT`, outside `MEDIA_ROOT`, with opaque filenames and no storage URL. Existing local document references retain a read fallback, so authorized historical previews continue to work. Existing legacy files are not moved or deleted automatically. A production reverse proxy/CDN must deny `/media/user_documents/` and avoid exposing `PRIVATE_DOCUMENT_ROOT`; migrate/remove legacy public copies under an approved operational plan. R2 continues to use the existing private bucket backend. Actual deployed bucket/proxy policy still needs verification.

Uploads are limited to nonempty files of at most 10MB. Pillow verifies images and their actual formats; oversized/animated images are rejected. `pypdf` parses nonencrypted PDFs of up to ten pages and rejects active content, annotations and embedded files. Parsing errors are generic, and private-parser diagnostics are suppressed. Protected streams use no-store, nosniff and sandbox headers. Existing preview blobs are revoked on close. No ID numbers, selfies, embeddings, provider payloads or permanent credentials are logged by the new integration.

Attempts are limited by a per-user hourly throttle and a database-enforced three-attempt daily cap under a user-row lock. Retries create evidence attempts, never another farmer account. A provider timeout is technical unavailability, not a failed match. Poll failures retain the last known result. Abandoned/expired sessions can be retried; expired registration capabilities direct the farmer to MAO instead of silently re-registering. MAO can document manual assessment and use its existing approval decision regardless of provider availability. No automatic rejection, approval or ban is introduced.

`expire_identity_sessions` is a dry run by default. After establishing policy and a schedule, `--execute` requests provider deletion for due attempts without legal/audit holds, explicitly disables retained face embeddings, and checks the provider's deletion outcome before clearing local provider references/result categories. Failed deletion keeps references for retry. Original registration documents, consent/assessment audit records and legitimate holds are not silently deleted. Their separate municipal retention schedule must be established before production; the implementation does not invent a government-record retention period. The provider's [deletion reference](https://docs.didit.me/sessions-api/delete-session) distinguishes operational deletion from a privacy-erasure instruction; a deletion response is not a legal erasure certificate.
